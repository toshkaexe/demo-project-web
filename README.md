# lavka-web

Фронтенд онлайн-магазина продуктов «Лавка» на Next.js 16 (App Router, React 19, Tailwind CSS 4).

Работает поверх бэкенда Lavka API (Java, Spring Boot, отдельный репозиторий): все данные — товары, заказы, пользователи — живут там, фронтенд ходит в API со своего сервера.

## Что умеет

| Кто | Что видит и может |
|---|---|
| **Гость** | смотреть каталог, собирать корзину. Войти нужно только при оформлении заказа, корзина при этом сохраняется |
| **Покупатель** (`CUSTOMER`) | всё, что гость, плюс: оформить заказ, видеть **свои** заказы и историю их статусов, отменить заказ, пока он в статусе «Оформлен», вести адреса доставки в профиле и выбирать активный, при заказе указать, на какой адрес везти |
| **Сотрудник склада** (`WAREHOUSE`) | видеть список товаров с остатками на складе и менять остатки, **все** заказы всех клиентов, видеть адрес доставки каждого заказа, проводить их по статусам: «Начать сборку» → «Собран» → «Выполнен», отменить новый заказ, смотреть историю статусов |

Страницы:

| Адрес | Что там |
|---|---|
| `/` | сразу открывает каталог (перенаправляет на `/catalog`) |
| `/catalog` | список товаров с кнопкой «В корзину» |
| `/login` | вход и регистрация, сюда ведёт кнопка «Войти» в шапке |
| `/basket` | корзина: количество, сумма, выбор адреса доставки, «Оформить заказ» |
| `/orders` | «Мои заказы» у покупателя, «Все заказы» у склада |
| `/stock` | только для склада: все товары с ценой и остатком, остаток можно изменить |
| `/profile` | профиль: email, роль, дата регистрации и адреса доставки (до 10), их можно добавлять, менять и удалять |

После входа покупатель попадает в каталог, сотрудник склада — сразу к заказам. У склада в меню «Лавка», «Заказы» и «Товары». В профиль ведёт пункт меню «Профиль» у покупателя и email в шапке у всех.

## Запуск

Нужны Node.js 20+ и запущенный бэкенд на `http://localhost:8080` (как его поднять — в README бэкенда).

```bash
npm install
npm run dev          # http://localhost:3000
```

Сборка и запуск в production-режиме:

```bash
npm run build
npm start
```

Проверки:

```bash
npx tsc --noEmit     # типы
npm run lint         # ESLint
```

### В Docker

Бэкенд запускается отдельно, своим `docker compose`, и должен отвечать на `http://localhost:8080`. Фронтенд-контейнер ходит к нему через `host.docker.internal`.

```bash
docker compose up -d --build     # http://localhost:3000
docker compose logs -f web       # логи
docker compose down              # остановить
```

- Образ собирается в три этапа (`Dockerfile`): зависимости → `next build` с `output: "standalone"` → итоговый образ на `node:22-alpine` только с `server.js`, нужными модулями и статикой. Приложение работает от пользователя `node`, не от root.
- Если порт 3000 занят (например, `npm run dev`): `WEB_PORT=3100 docker compose up -d`.
- После изменений в коде пересобрать: `docker compose up -d --build`.

### Настройки

| Переменная | По умолчанию | Для чего |
|---|---|---|
| `LAVKA_API_URL` | `http://localhost:8080`, в Docker — `http://host.docker.internal:8080` | адрес бэкенда |
| `COOKIE_SECURE` | `true` в production, `false` в разработке; в Docker — `false` | флаг `Secure` у cookie: браузер отправляет их только по HTTPS. За HTTPS ставьте `true` |
| `WEB_PORT` | `3000` | порт на хосте для `docker compose` |

Переменную можно положить в `.env.local` (файл не коммитится).

### Демо-данные

Скрипт бэкенда `./src/test/fill_all.sh` заводит товары, покупателей `customer1…5@gmail.com` (пароль `123456`) с заказами и сотрудника склада `warehouse@lavka.local`. Роль `WAREHOUSE` выдаётся только в базе бэкенда, через сайт её получить нельзя.

### Авторизация

- Бэкенд выдаёт пару JWT: access (15 минут) и refresh (30 дней, одноразовый).
- Токены хранятся в cookie `access_token` и `refresh_token` с флагом `httpOnly`, поэтому JavaScript в браузере их не видит. Запросы к API делает сервер Next.js, а не браузер, поэтому CORS для фронтенда не нужен.
- `proxy.ts` перед `/catalog`, `/basket`, `/orders`, `/stock` и `/profile` проверяет срок access-токена и, если он истёк или истекает, получает новую пару через `POST /auth/refresh`. Пока жив refresh-токен, заново входить не нужно.
- Server Actions делают то же самое через `authFetch` из `lib/session.ts`: при ответе `401` один раз обновляют токены и повторяют запрос.
- «Выйти» вызывает `POST /auth/logout`, который отзывает оба токена, и удаляет cookie вместе с корзиной.

### Корзина

На бэкенде корзины нет: `POST /orders` принимает весь список покупок сразу. Поэтому корзина хранится в cookie `cart` как `{ "id товара": количество }`. Для неё действуют те же ограничения, что у API: не больше 100 позиций и 1000 штук одного товара. Положить больше, чем есть на складе, нельзя, но сам остаток покупателю не показывается.

### Статусы заказов

```
Оформлен ──► Собирается ──► Собран ──► Выполнен
   │
   └──► Отменён
```

Переходы и права совпадают с бэкендом (`lib/order-status.ts`): покупатель может только отменить свой заказ из «Оформлен», остальное делает склад. Если статус успел поменять кто-то другой, бэкенд отвечает `409`, страница показывает это и обновляет список.

### Остатки на складе

На `/stock` у каждого товара есть поле с количеством, кнопки «−» и «+» и «Сохранить». Кнопка активна, только если число изменилось; сохранить можно и клавишей Enter. Допустимо целое число от 0.

В API нет отдельного запроса для остатка: `PUT /products/{id}` заменяет товар целиком. Поэтому `app/actions/product.ts` сначала получает актуальные название и цену товара, а потом отправляет их обратно вместе с новым количеством. Покупателю бэкенд такой запрос не разрешает (`403`).

### Адреса доставки

Адреса хранит бэкенд, ручки `/users/me/addresses` (`GET`, `POST`, `PUT /{id}`, `DELETE /{id}`). Каждый видит и меняет только свои адреса.

- Обязательные поля: получатель, страна, город, индекс, улица, дом. Квартира и комментарий курьеру необязательны.
- Длины полей проверяются ещё на сайте (`ADDRESS_FIELDS` в `lib/api.ts`, те же лимиты, что в базе), поэтому ошибка показывается у конкретного поля. Если сохранить не удалось, введённое не стирается.
- Не больше 10 адресов на пользователя: столько разрешает бэкенд.
- **Активный адрес** отмечен в профиле зелёной меткой «Активный»: туда по умолчанию едут заказы. Первый адрес становится активным сам, другой выбирается кнопкой «Сделать активным» (`PUT /users/me/addresses/{id}/active`). Если удалить активный, активным станет самый старый из оставшихся.
- **При оформлении** в корзине есть блок «Куда доставить»: все адреса, отмечен активный, можно выбрать любой другой. Выбор в корзине не меняет активный адрес. Если адресов нет, его можно добавить прямо там, без адреса кнопка «Оформить заказ» неактивна. В `POST /orders` уходит `address_id`.
- **В заказе** хранится копия адреса (`delivery_address`), её видно в «Моих заказах» и у склада. Если потом поменять или удалить адрес в профиле, у старых заказов адрес не изменится.

## Известные ограничения

- Склад может менять только остаток. Создавать, переименовывать, менять цену и удалять товары через сайт пока нельзя, хотя API это позволяет.
- Если кто-то поменяет цену или название товара в тот же момент, когда склад сохраняет остаток, эта правка может затереться: `PUT` отправляет всё, что было прочитано за мгновение до этого.
- refresh-токен одноразовый. Если две вкладки одновременно попробуют обновить истёкший токен, одна из них может отправить на страницу входа.
- Корзина живёт в cookie конкретного браузера и не переносится между устройствами.
